# 变更核验（change-verify）

「写完了」和「真的生效」是两件事。本技能只做一件事：把这两件事的差距找出来，**列给用户看，不替用户决定，也不顺手改**。

## 何时用、何时不用

- 用：改了代码 / 配置 / 脚本 / 规则文件 / 插件，准备提交或交付；排查结论要写成定论。
- 不用：纯文档、纯计划、纯调研；也不要在实现还没跑通时先核验（先让 L1 的测试过）。
- 紧急热修可只跑 L1，但报告里必须写「未做 L2 找茬」及原因。

## 铁律

1. **只读**：核验过程不改任何仓内文件、不改配置、不重启服务；需要重启才能验证的，写成 P1 待办交给用户。
2. **不自动修**：发现问题只列清单，等用户发话再修。
3. **不跑破坏性命令**：不用 `git stash`/`checkout` 去"临时看效果"，不在 `/tmp` 或仓外造替代环境。
4. **无证据写推测**：结论必须对应命令输出、代码行、时间戳；拿不到证据就标「推测」。
5. **P0/P1 阻塞交付**：未解决前不提交、不宣称完成；用户明确放行才可例外，且报告里记一句。

## 输入

开工前先写清四项，缺一项就先去问或去查：

- 目标仓绝对路径；
- 变更范围：`git status --short`、`git diff --stat`、未跟踪文件、最近提交号；
- 该仓验收命令（看仓内 `AGENTS.md` / `package.json`，例如 `npm test`、`./scripts/check.sh --repo <repo>`）；
- 运行入口：改动怎么被加载（进程名、pid、symlink、缓存、是否需要重启）。

## L1 自检（AI 自己跑，全部可判定）

按顺序执行，每项记一条命令回执；**不许用"之前跑过"代替现在跑**。

1. **变更清单**：`git -C <repo> status --short` + `git diff --stat`；确认只含本任务文件，无跨仓混提迹象。
2. **测试真跑**：在仓根跑验收命令，记退出码与最后 3 行输出；失败即 P0，停下先修。
3. **门禁**：有文档改动时，在工作区根跑 `./scripts/check.sh --repo <repo>`；仓内没有 `check.sh` 时改用该仓的验收命令。
4. **生效性**（今天最常漏）：改动文件是否真的会被运行时加载——
   - 找加载链：`grep -rn "risk-allow.js" <repo>`、看入口 `index.js` 的 `import`；
   - 比时间：`ps -o pid,lstart,args -p <pid>`，进程启动时间早于改动时间 ⇒ 旧代码仍在跑，P1；
   - 看指向：`ls -l <安装路径>` 确认 symlink 指的就是这个 checkout；
   - 进程启动时只读一次的东西（规则文件、配置、缓存）⇒ 必须重启才算生效；
   - **同一模块装在多处时逐个比对**：多个 profile（`~/.dsh/profiles/*/node_modules/...`）、多个 systemd 单元、常驻 agent 进程，漏掉任何一个都是"部分生效"。
   - 引用 pid 前先确认它还活着（`ps -p <pid>`），已消失的进程不能作为当前证据。
5. **真实入口回放**：用真实输入跑一遍（历史命令回放、HTTP 请求、CLI），把关键输出行贴进报告；这是唯一能证明"生效"的证据。
6. **文档一致**：README / README.en / STATUS / PLAN 的措辞与代码行为逐条对照；PLAN 的 `implementation_status` 是否已改。
7. **证据留档**：报告里贴输出原文，不写"ok""通过"了事。

## L2 找茬（派一个 fresh subagent）

L1 通过后派 `subagent`（**fresh，不要 fork**），它不继承你的推理，只看事实。prompt 用下面模板，把尖括号填实：

```text
你是独立核验者，不参与本次实现。只读，不改任何文件，不重启服务。
工作区根 <绝对路径>；目标仓 <repo>。
变更：<git diff / 提交号 / 文件清单>。
该仓验收命令：<命令>；运行入口：<加载方式，是否需要重启>。
实现者声称的结论：<一句话，例如"改完链接检查后这两条命令不再弹卡">。

找出这次改动的问题，按严重度排列。重点攻击：
1) 新增的放行/忽略/早退分支，能不能用最坏输入绕过：空值、不可解析值（new URL 失败）、引号/换行/超长、变量占位符；
2) 新测试是否真覆盖改动：哪一行改动删掉后，新测试仍然会通过？
3) 结论是否只验证了第一个假设：哪些错误被展示层折叠了（截断、[0]、默认值、只显示首个 URL）；
4) "已生效"的证据是否成立：加载路径、进程启动时间、进程内缓存、安装包指向；
5) 回归面：缓存语义、文件/规则格式、审批流、并发、错误提示文案。
每条给：编号 | P0/P1/P2 | 文件:行 | 问题 | 证据（命令输出或代码行） | 建议动作。
没证据的标「推测」。最后给「是否阻塞交付：是/否」和一句理由。
```

收它结论后**自己复核一遍**再列给用户，别转述它的猜测；它对不上的条目要么补证据，要么降级。

## 输出格式

给用户一张表，外加两行结论：

| # | 严重度 | 位置 | 问题 | 证据 | 建议动作 |
| --- | --- | --- | --- | --- | --- |

```text
L1：测试 <通过/失败>；门禁 <PASS/FAIL>；生效性 <已重启验证 / 未生效，需重启 <命令>>
结论：阻塞交付（P0/P1 未解决）/ 不阻塞
```

## 常见漏检（真实事故换来的）

- **改完没重启**：插件/服务在进程启动时加载代码或规则，改了文件不等于生效（`dsh web` 的 `RiskRuleStore` 就是典型）。
- **只验证第一个假设**：审批卡只显示原因里的第一个 URL（`unknown[0]` / `slice(0,120)`），真正的坏输入被折叠在后面；排查到"看着像的"原因就收工。
- **放行分支自己成了漏洞**：为了"容忍不可解析值"而写的 `every()` / `filter`，在空集合上会变成"全部放行"。
- **测试写给检查者看**：新测试断言的是旧行为，删掉改动照样通过。
