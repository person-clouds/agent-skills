# 文档精简（doc-slim）

## 何时用

- `./scripts/check.sh` 输出 `超过建议上限 N 行`（含 `--strict` 失败）。
- 要新建或大改文档，预估会超限——先按本技能写成合规版本，不要先写长再删。
- 用户说“太长了”“压一下”“合并重复”。

## 铁律

1. 只动文档，不改代码、配置、仓库结构。
2. 不确定某段是否唯一时，先搜索再决定；删掉的内容必须有去处（合并到主文档、迁到项目仓、归档）。
3. 不为了过检查删安全红线、授权边界、例外条件、必要命令、非显然事实。
4. 不在正文里留“已精简”“见上文”之类的空话。
5. 默认不提交；用户要求提交时按仓库规范逐仓提交。

## 步骤

### 1. 确认目标与上限

```bash
cd <工作区根>
./scripts/check.sh --repo <repo>      # 或 --all，拿到超限文件与行数
```

对照 `scripts/docs-policy.json` 的 `line_limits` 确认该文件上限（没有该文件时按文档自身声明的上限）；计划类文档另有 `## 篇幅说明` 放宽到 400 行。

### 2. 找权威源与重复

```bash
rg -n "<关键句/小节标题>" . --glob '!**/node_modules/**' --glob '!**/.git/**' --glob '!doc/archive/**'
```

- 同一主题在其他文档已有正文 → 本处只留链接。
- 内容属于某项目 → 迁到该项目仓 `README.md` / `SPEC.md` / `docs/`。
- 历史过程、复盘、一次性记录 → `doc/archive/`。
- 需要语义比对时可用本机的语义检索工具（RAG MCP 等），但它可能降级为词法检索，结论以原文为准。

### 3. 分类再动手

逐段标记：

| 类别 | 处理 |
|---|---|
| 结论、硬约束、边界、例外、入口、必要命令 | 保留，尽量压成一行 |
| 背景论证、推导、过程日志、重复示例 | 删除或移 `archive/` |
| 同一规则多处出现 | 留一处主文档，其余改链接 |
| 可现查的版本号、路径细节 | 删除或指向 `PROJECT_INDEX` / `STATUS` |

### 4. 重写

- 按工作区文档规范（如 `doc/specs/documentation-rules.md`）第 2、3 节：先结论，再约束，再入口。
- 表格优先于长段落；列表每项一行，不写三层嵌套。
- 保留原有标题层级和 `## 改动记录`（计划文档必须有）。
- 计划确实需要保留交接证据时，加 `## 篇幅说明` 写原因，而不是硬删关键步骤。

### 5. 验证

```bash
./scripts/check.sh --repo <repo>
./scripts/check.sh --all --strict
```

必须无该文件的超限 WARN；断链、计划元数据等 FAIL 一并修掉。

### 6. 汇报

输出：原行数 → 新行数、删掉/合并的段落及去处、验证命令与结果。若仍有超限，说明原因和下一步，不要假报通过。
